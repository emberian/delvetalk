1. **P1 — Public requests are not bound to a particular service or world identity.**  
   [ATPROTO §2](docs/ATPROTO.md:89), [request.json:44](lexicons/town/delvetalk/request.json:44). A request has only an optional local world name, defaulting to `town`. Two deployments watching the same repository can execute the same signed request under the resident’s authority. A newly installed consumer can also execute years-old requests: `createdAt` establishes neither expiry nor freshness. Signature verification does not resolve either ambiguity.  
   **Fix:** require a target service/world DID, define expiry and initial-import behavior, and durably bind each consumed request URI to its first accepted CID and result. Check the target before admission.

2. **P1 — The public answer schema instructs publishers to disclose caller-private content.**  
   [answer.json:35](lexicons/town/delvetalk/answer.json:35), [ATPROTO §2](docs/ATPROTO.md:118). The record describes `card` as what the **caller** may read and `offers` as cards offered to that caller. Those fields are then mirrored publicly. A public request can invoke an operation whose result includes private state; public input does not make its output public. This contradicts the prose’s public-projection requirement.  
   **Fix:** separate public `answer` records from authenticated `answerView` responses. Define projection for every field—including refusal text, offers, fired rules and revealed lines—and publish only the anonymous projection.

3. **P1 — OAuth discovery permits server-side requests to attacker-selected internal endpoints.**  
   [oauth.py:108](transport/oauth.py:108), [oauth.py:129](transport/oauth.py:129). An attacker-controlled DID document or authorization-server metadata can supply HTTPS URLs resolving to private addresses. URL validation checks scheme and syntax, while the shared HTTP transport performs ordinary DNS resolution. Starting a login therefore initiates internal GETs and potentially PAR/token POSTs. HTTPS and disabled redirects do not prevent this.  
   **Fix:** use a hardened discovery client that rejects private, loopback, link-local and reserved destinations, including after DNS resolution, and prevents DNS rebinding. Apply it to every discovered endpoint. This is explicitly part of the [OAuth security requirements](https://atproto.com/specs/oauth#security-considerations).

4. **P1 — Carry and signing-key rotation violate repository revision continuity.**  
   [REPO:37](docs/REPO.md:37), [REPO:60](docs/REPO.md:60), [repo.py:87](transport/repo.py:87). After carry, `Signed` starts its clock at zero and recognizes only subsequent `advance:` entries; its first revision can regress to 1970 despite continuing journal heights. Rotation regenerates different commit CIDs at the **same revisions**. Followers cannot treat either operation as ordinary forward progress, and rotation manufactures the same-revision divergence REPO calls fork evidence.  
   **Fix:** persist repository revision state independently of journal compaction. Carry and rotation must create a new, higher revision; rotation can preserve the MST root. Preserve published records or explicitly reconcile their removal. The [repository specification](https://atproto.com/specs/repository#commit-objects) calls for a new commit on rotation.

5. **P1 — The façade impersonates repository APIs while returning non-record CIDs and unrelated proofs.**  
   [REPO:146](docs/REPO.md:146), [repo.py:190](transport/repo.py:190), [repo.py:382](transport/repo.py:382). Receipt/object/source responses advertise the entry/state/module CID rather than the CID of `value`; adding `$type` alone already changes the bytes. Law listings omit the required `cid`. A `sync.getRecord` request for `receipt/<slug>` proves membership at `entry/<rev>`, not the requested path. Strict clients reject these responses or cannot authenticate their references.  
   **Fix:** reserve `com.atproto.repo.*` and `sync.*` for actual public MST records. Put private projections and application proofs behind `town.delvetalk.*`; give any real record its own content CID. See the [standard listing schema](https://raw.githubusercontent.com/bluesky-social/atproto/main/lexicons/com/atproto/repo/listRecords.json).

6. **P1 — Three lexicons contain structures rejected by the reference Lexicon validator.**  
   [card.json:43](lexicons/town/delvetalk/card.json:43), [openSession.json:21](lexicons/town/delvetalk/openSession.json:21), [listSessionRecords.json:40](lexicons/town/delvetalk/listSessionRecords.json:40). `doors.items`, `from`, and `records.items` embed `type: object` directly. The reference validator permits these nested objects through references, not inline definitions. Registering the schemas or generating clients fails.  
   **Fix:** move each nested object into a named `defs` entry and use `ref`. Validate the schema documents themselves, not just `"lexicon": 1` and emitted records. [Reference schema implementation](https://raw.githubusercontent.com/bluesky-social/atproto/main/packages/lexicon/src/types.ts).

7. **P1 — The polling watermark silently loses valid requests.**  
   [ATPROTO §2, “Seeing it”](docs/ATPROTO.md:99). Record keys are not a reliable insertion sequence. A resident can upload an older TID, import records, or update a previously invalid request below the last answered key. The repository revision changes, but scanning only beyond that key misses the request forever. Polling also cannot observe records created and deleted between polls.  
   **Fix:** reconcile collection membership/CIDs when a revision changes, or consume verified repository diffs with resynchronization. Track consumed URIs separately from scan progress. Explicitly require requests to remain present until acknowledged. ATProto itself warns that chronological ordering depends on TID generation that [cannot generally be relied upon](https://atproto.com/specs/repository#repository-paths).

8. **P1 — Discovery remains tied to one PDS and one DID method, so migration breaks participation.**  
   [ATPROTO:99](docs/ATPROTO.md:99), [ATPROTO:106](docs/ATPROTO.md:106), [oauth.py:124](transport/oauth.py:124). After a resident moves off `pds.delve.town`, its new requests disappear from the designed discovery path. Fetching proofs from the old PDS can instead accept stale repository state when its signing key remains valid. Meanwhile, the proposed resolver reuse accepts only `did:plc` and sends it to `plc.directory`; the hosted `did:web` residents cannot use it.  
   **Fix:** maintain a DID-based participant registry, resolve each participant’s current PDS, refresh identity on changes and verification failures, and preserve consumption state across migration. Implement method-specific `did:plc` and hostname-level `did:web` resolution. [DID specification](https://atproto.com/specs/did).

9. **P1 — The bare-audience compatibility exception cannot identify the forwarding PDS.**  
   [ATPROTO:132](docs/ATPROTO.md:132). A service JWT’s `iss` identifies the resident, not `did:web:pds.delve.town`; its signature does not attest which server forwarded the HTTP request. Thus “accept bare DID only from tokens forwarded by” that PDS is not enforceable from the token. The current reference proxy still emits bare-DID audiences, so this is an immediate interoperability issue.  
   **Fix:** define an explicit, narrowly scoped legacy-audience policy or require an authenticated transport relationship with the proxy. Do not infer forwarding identity from `iss`. Also specify required `typ`/`iat` validation and the caller’s PDS `rpc` authorization. [Reference proxy](https://raw.githubusercontent.com/bluesky-social/atproto/main/packages/pds/src/pipethrough.ts), [service-auth requirements](https://atproto.com/specs/xrpc#inter-service-authentication-jwt).

10. **P1 — Journal height cannot also be the firehose sequence number.**  
    [ATPROTO:69](docs/ATPROTO.md:69). `#identity` and `#sync` consume sequence positions without adding journal entries; multiple worlds have overlapping heights; carry removes the source of historical events. Emitting identity “at connect” also leaves its position relative to backfill undefined. Recomputed events can reuse sequence numbers or change the contents behind an existing cursor. Consumers may disconnect or miss events.  
    **Fix:** maintain a durable, endpoint-wide event sequence and retained event log, separate from world heights and repository revisions. Define the backfill window and `OutdatedCursor`/`FutureCursor` behavior. [Event-stream sequencing](https://atproto.com/specs/event-stream#sequence-numbers).

11. **P1 — One commit event per height lacks a valid overflow and proof-construction rule.**  
    [ATPROTO:60](docs/ATPROTO.md:60), [ATPROTO:71](docs/ATPROTO.md:71). One turn can change many dependent cards. The proposed event can exceed 200 operations or the 2,000,000-byte CAR limit; its listed fields also omit `rebase`, still required by the published lexicon. Reusing a changed-block `getRepo?since` slice does not establish that contextual nodes needed for operation inversion are included.  
    **Fix:** budget encoded events, use `#sync` plus full resynchronization when necessary, include compatibility-required fields, and construct/test inversion-complete proofs for updates and deletions. Bound individual records as well. [Subscription schema](https://raw.githubusercontent.com/bluesky-social/atproto/main/lexicons/com/atproto/sync/subscribeRepos.json), [sync limits](https://atproto.com/specs/sync#commit-events).

12. **P1 — The signed index’s head reference creates a hash cycle.**  
    [ATPROTO:50](docs/ATPROTO.md:50), [ATPROTO:63](docs/ATPROTO.md:63), [ATPROTO:81](docs/ATPROTO.md:81). The index is inside the signed tree, includes the signed head copied from, and is supposed to have identical bytes in both repositories. If that means the commit containing the index, its CID depends on itself. If the head is added only in the mirror, the promised byte/CID equality fails.  
    **Fix:** keep the signed index free of its containing commit CID. Publish a separate mirror checkpoint referencing the completed source commit, or explicitly reference the preceding commit and define the lag.

13. **P2 — Proxied private sessions are private from other residents, not from their PDS.**  
    [ATPROTO §3](docs/ATPROTO.md:171), [privacy table](docs/ATPROTO.md:193). `atproto-proxy` terminates TLS at the resident’s PDS and forwards plaintext application requests over another connection. The PDS sees scratch contents, previews and responses, can retain them, and normally holds the resident’s signing key. “Kept only by the caller” and exclusive resident authorship are therefore stronger guarantees than this architecture provides.  
    **Fix:** explicitly include the PDS in the confidentiality and impersonation trust boundary. Stronger confidentiality requires direct transport or application-level encryption with separately controlled keys. [Proxy semantics](https://atproto.com/specs/xrpc#service-proxying).

14. **P2 — Equal CIDs do not make strong references portable or permanently retrievable.**  
    [ATPROTO:56](docs/ATPROTO.md:56), [ATPROTO:112](docs/ATPROTO.md:112), [defs.json:226](lexicons/town/delvetalk/defs.json:226). A strong reference includes a repository URI as well as a CID. Copying identical bytes into another repository does not retarget that URI. Updating `card/<id>` or a page can also make the referenced version unavailable; standard repositories do not promise historical retrieval. Moreover, card text alone cannot reconstruct a card-record CID containing object, version, wants and doors.  
    **Fix:** define a canonical source URI and explicit mirror mapping; retain immutable versions where paint/books require them. Return the complete referenced record or a complete strong reference. [Strong-reference schema](https://raw.githubusercontent.com/bluesky-social/atproto/main/lexicons/com/atproto/repo/strongRef.json).

15. **P2 — Shared sessions have no unambiguous address or reader/write distinction.**  
    [ATPROTO:165](docs/ATPROTO.md:165), [getSession.json:14](lexicons/town/delvetalk/getSession.json:14). Sessions are stored under `(holder, name)` but exposed as `scratch/<name>`. If Alice and Bob both have `scratch/test`, a named reader cannot specify whose session to access. The same admission paragraph covers acts and reads, without defining whether named readers may mutate or publish. Recreating an expired name adds another aliasing problem.  
    **Fix:** return an opaque session identifier binding holder and incarnation; use it in every operation. Define read, write, share and publish permissions separately, enforced by the host.

16. **P2 — Public answers to XRPC acts cannot satisfy the answer-record contract.**  
    [ATPROTO:127](docs/ATPROTO.md:127), [answer.json:9](lexicons/town/delvetalk/answer.json:9), [answer.json:12](lexicons/town/delvetalk/answer.json:12). Every XRPC act supposedly produces a public `answer`, but that record requires a request strong reference and is keyed by the requesting DID plus request rkey. An XRPC `intent` has neither a repository record nor an rkey. Inventing a URI would produce a reference that cannot resolve or be proved.  
    **Fix:** define distinct record-request and XRPC provenance variants, a deterministic answer-key scheme for both, and which XRPC metadata may become public.

17. **P2 — Execution-critical constraints exist only in prose, and several response invariants are unrepresentable.**  
    [defs.json:6](lexicons/town/delvetalk/defs.json:6), [request.json:18](lexicons/town/delvetalk/request.json:18), [defs.json:208](lexicons/town/delvetalk/defs.json:208). `{}` and mixed spell/object calls validate; `mode: act` permits eight calls; `knownValues` does not exclude `try` or unknown modes; preview outputs permit receipts. Unbounded fields, traces and arrays lack an aggregate record-size contract. Consumers cannot infer deterministic rejection behavior from these lexicons.  
    **Fix:** use discriminated call/result variants, define semantic validation and rejection codes, require nonempty intents, and impose byte/count/depth budgets. Keep preview results structurally separate from committed receipts. [Lexicon semantics](https://atproto.com/specs/lexicon).

18. **P2 — Mirroring has no label-subject or moderation propagation contract.**  
    [ATPROTO:78](docs/ATPROTO.md:78), [ATPROTO:187](docs/ATPROTO.md:187). A label targeting the world’s card URI does not automatically apply to its copy under the posting account, even when the CID matches. Consequently, a client moderating the original can display the mirrored copy unlabelled. Permanent replay also needs an explicit policy for withdrawn public projections; local object laws cannot control already distributed records.  
    **Fix:** specify canonical moderation subjects and mirror mappings, which labelers are trusted, and how negation, expiry, account status and takedowns affect served projections. Preserve original signed label subjects; use separately attributed decisions for copies. Labels are optional application metadata, not confidentiality controls. [Label subjects and lifecycle](https://atproto.com/specs/label).
